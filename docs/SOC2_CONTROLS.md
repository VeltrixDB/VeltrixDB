# VeltrixDB — SOC 2 Trust Service Criteria Mapping

This document maps VeltrixDB's built-in capabilities to the SOC 2 Trust Service Criteria (TSC). Provided as a starting point for an auditor's evidence-gathering; **a SOC 2 attestation is a property of your operating environment, not of VeltrixDB alone**. The table below states what the database provides and what the operator must implement to satisfy each criterion.

| TSC | Criterion summary | VeltrixDB capability | Operator obligation |
|-----|---|---|---|
| CC6.1 | Logical access controls | RBAC (`--auth-config`; `AUTH <user> <password>` required before any command), per-namespace keyspaces (`NSPUT`/`NSGET`/…), mTLS (`--tls-cert`/`--tls-key`/`--tls-ca`); `/admin/*` is loopback-only unless `--admin-token` (env `VELTRIX_ADMIN_TOKEN`) is set, then requires `Authorization: Bearer` or `X-Admin-Token` (`adminapi/guard.go`) | Provision unique users per service, rotate credentials, set `--admin-token` and still deny network ingress to the metrics/admin port (`/metrics`, `/healthz`, `/readyz` are never authenticated) |
| CC6.6 | Restrict data transmission to authorized parties | TLS 1.3 listener (`--tls-addr`, default `:9443`; `MinVersion: TLS13` in `security/tls.go`), mTLS client cert verification; inter-node TLS (`--cluster-tls-cert`/`--cluster-tls-key`/`--cluster-tls-ca`, `--cluster-mtls`); inter-node transfer listener (key migration + distributed search) signed with HMAC-SHA256 via `--cluster-secret-file` (or env `VELTRIXDB_CLUSTER_SECRET`), or cluster mTLS | Use mTLS in production; load only signed certs; set the same cluster secret on every node (the server logs a warning when the transfer listener is unauthenticated) |
| CC6.7 | Encrypted data at rest | AES-256-GCM of VLog values (`--encrypt-at-rest`) on every write path — `PUT`, `MPUT` / batched writes and the atomic ops (CAS / INCR / DECR / SETNX; builds before 2026-10 stored those in plaintext, and such values stay plaintext until next updated); 32-byte key from `VELTRIXDB_ENCRYPTION_KEY` (base64) or `--encryption-key-path`; startup fails if the key is missing or not 32 bytes. Keys are not encrypted, and there is no key rotation (one key per data dir) | Manage the master key in KMS / sealed secret; never commit key material to source. PITR archive segments hold values decrypted — encrypt and access-restrict the archive location |
| CC6.8 | Anti-malware / image hygiene | Single-binary distribution; `Dockerfile` runtime stage is `gcr.io/distroless/cc-debian12` (glibc, no shell) | Scan published images (Trivy / Snyk); pin the image SHA256 in your deployment manifests |
| CC7.1 | Detection of vulnerabilities | `govulncheck ./...` runs in CI (`security` job, `.github/workflows/ci.yml`). It is **non-blocking** (`continue-on-error: true`) and its output is only in the job log | Triage vulncheck output weekly (findings do not fail CI); subscribe to Go security mailing list |
| CC7.2 | Monitoring of components | Prometheus metrics on `--metrics-addr` (`metrics/prometheus.go`, ~80 families: storage, WAL, VLog, cache, scrubber, cluster, replication, failure detector). `metrics/hardware.go` (runtime / process / system / disk) is **not** registered by `cmd/server`, and no Go runtime or `process_*` collector is either. `/healthz` and `/readyz` endpoints, a `PrometheusRule` with 10 default alerts in `monitoring/prometheus-rules.yaml` (write throttle, GC stalled, VLog read errors, scrub corruption, cache hit rate, read P99, node failure, cluster shrank, disk usage, restart) | Run a Prometheus / Alertmanager stack with paging integration; review alert noise quarterly. The disk-usage alert needs node-exporter; the restart alert uses `process_start_time_seconds{job="veltrixdb"}`, which VeltrixDB does not export — supply it (e.g. a process exporter) or that alert never fires |
| CC7.3 | Anomaly identification | Slow-op trace ring buffer at `/traces` (default 50 ms slow threshold, `tracing/tracing.go`); per-disk read-latency EWMA (admission control / GC throttling); `veltrixdb_scrub_corruption_total` | Define normal-baseline; alert on deviations |
| CC7.4 | Security incident response | DR runbook (`docs/DR_RUNBOOK.md`) | Rehearse the runbook quarterly; capture post-mortems |
| CC7.5 | Recovery from incidents | Online backup via `POST /admin/backup` / `veltrix backup` (full, incremental); offline `veltrixdb-backup` (`cmd/backup`: full, incremental, restore, cloud upload/download, PITR `restore-pitr` with `--archive-dir` WAL archiving — stopped server only; every engine holds an exclusive `<data-dir>/LOCK`, so the tool refuses a live server's dirs instead of corrupting them); Raft log catch-up / InstallSnapshot; raw-mode crash recovery (Invariant 27); WAL replay | Volume snapshots (if you use them) are operator-side, not a VeltrixDB feature; test restore at least twice a year; maintain quorum across availability zones |
| CC8.1 | Authorization of changes | None in the database. This repository contains no Helm chart or PodDisruptionBudget (deployment manifests live outside it) | Version your deployment manifests; require PR review on every change; block deploys outside change windows |
| A1.1 | Process capacity | Per-disk throughput / latency / file-bytes metrics; admission control with documented thresholds (Invariant 22) | Capacity plan against `vlog_file_bytes` growth; pre-provision before crossing 70 % |
| A1.2 | Backup of data | VLog + WAL durably fdatasync'd; WAL group commit (Invariant 19, 20); `POST /admin/checkpoint`; `POST /admin/backup` (full / incremental); continuous WAL archiving for PITR (`--archive-dir`) | Schedule a backup job; verify by occasional restore-to-staging |
| A1.3 | Disaster recovery testing | Soak script at `scripts/soak.sh`; bench harness `scripts/bench.sh` regression-gates packing density and GC emergency | Run soak monthly to detect drift; gate releases on bench pass |
| C1.1 | Confidentiality of information | At-rest encryption + JSONL audit log (`--audit-log`, `storage/audit.go`). It records one entry per key for every engine write path: `PUT` / `DEL` (single-key writes, MPUT, coalesced pipelined PUTs, TXN commit and Raft batch apply) and the atomic ops as `CAS` / `INCR` / `DECR` / `SETNX`, including outcomes that wrote nothing (`mismatch`, `not_found`, `exists`, `err`). Reads and admin calls are not recorded. The `actor` field is never filled in. Writes are async and a record is **dropped** when the channel is full (`audit_dropped_total` in `/admin/stats`). Values are never logged | Ship audit log to immutable retention (Loki / S3 Object Lock); restrict who can read it; alert on `audit_dropped_total > 0`; record user identity outside VeltrixDB if a control needs it |
| C1.2 | Disposal of confidential information | `BLKDISCARD` on raw NVMe (Invariant 26); `fallocate(PUNCH_HOLE)` on file-backed disks during VLog GC | Document key destruction in tenant offboarding |
| PI1.1 | Processing integrity inputs | Binary protocol frame size caps (`frame too large`); per-namespace quotas (`SetNamespaceLimit`, `POST /admin/quotas` with `writes_per_sec`, `burst`, `max_keys`) | Enable quotas per tenant from day one |
| PI1.4 | Output completeness/accuracy | CRC32C on every VLog record (write + read verification) and on every WAL record (binary format, the default: the whole record, header included; verified on crash replay and PITR restore); background scrubber re-validates (`--scrub-mb-per-sec`, default 50 MB/s per disk) | Alert on `veltrixdb_scrub_corruption_total` increase (`VeltrixDBScrubCorruption` in `monitoring/prometheus-rules.yaml`) |
| PI1.5 | Processing integrity errors | Admission control + GC emergency logs; scrubber emits `[scrub] disk=N offset=O ... MAGIC MISMATCH` / `... CRC MISMATCH` for every detection | Forward error logs to SIEM; on-call must be paged on corruption |

## Audit evidence checklist

For an auditor in the room, the operator should be able to produce:

1. **Encryption proof** — `curl -s localhost:2112/admin/version` (from loopback, or with the admin token) showing `"encryption_enabled": true`; `kubectl get pod POD -o jsonpath='{.spec.containers[*].env[?(@.name=="VELTRIXDB_ENCRYPTION_KEY")]}'` (shows the Secret reference, not the key; the image is distroless, so `kubectl exec … env` does not work) and a `kubectl describe secret` on the Secret it references.
2. **Access control proof** — the `--auth-config` JSON showing roles + users, the startup log line `[auth] RBAC enabled  config=<path>`, and a client transcript of a rejected command before `AUTH` and of a failed `AUTH`. The server does not log successful or failed logins, so they cannot come from its logs.
3. **TLS proof** — `openssl s_client -connect veltrixdb.svc:9443 -showcerts` showing the chain. mTLS proof: an attempt without a client cert is rejected.
4. **Backup proof** — backup directories (or `veltrixdb-backup list-cloud` output) whose `manifest.json` `timestamp_ns` falls within the last 7 days, or your volume-snapshot listing if you snapshot volumes instead.
5. **Audit log proof** — the last 100 lines of the `--audit-log` file (NDJSON), `audit_dropped_total` from `/admin/stats`, and a query showing the audit log has been shipped to Loki / Splunk for the last 30 days.
6. **Monitoring proof** — Grafana dashboard JSON (`grafana/`) and a screenshot of an alert firing in the past 90 days.
7. **DR proof** — minutes of the most recent DR drill (run quarterly per the runbook).
8. **Vulnerability scanning proof** — most recent `govulncheck` output (the `Security — govulncheck` job log; it is not uploaded as an artifact) and the resolution status of any findings.
9. **Change management proof** — recent PR reviews on your deployment manifests showing two-person sign-off.
10. **Capacity proof** — Prometheus query for `veltrixdb_vlog_file_bytes` over 30 days showing < 70 % of allocated PVC.

## What VeltrixDB does NOT yet provide (gaps to disclose)

- **Tamper-evident, complete audit log**: the audit JSONL is appended locally and shipped externally; it is not cryptographically chained, it covers engine writes (all write paths, including atomic ops) but not reads, admin calls or TTL expiry, carries no user identity, and drops records under back-pressure. If your control framework requires hash-chained audit, ship the log to an immutable backend (S3 Object Lock, Worm-mounted volume).
- **Field-level encryption**: at-rest encryption applies to whole values. If you need per-field encryption (column-level), implement at the application layer.
- **HSM / KMS integration and key rotation**: the master key is loaded from an environment variable or a key file, and there is no rotation path (values written under one key cannot be read under another). Use Kubernetes Secrets backed by a CSI driver (e.g. AWS Secrets Manager CSI) to source the key from a KMS at pod startup; do not store the raw key in the cluster.
- **Login auditing**: successful and failed `AUTH` attempts are not logged.
- **PII detection / redaction**: no built-in scanner. If applicable, run an external DLP scanner over the audit log.
